Harness Engineering: conceptos clave

La idea central que viene consolidándose en 2026 es esta ecuación: Agente = Modelo + Harness. El modelo aporta el razonamiento crudo, pero el harness es la capa de ingeniería que convierte ese razonamiento probabilístico en acción confiable, verificable y segura. Es literalmente la diferencia entre un agente que funciona en una demo y uno que funciona en producción todos los días.

Es la tercera fase de madurez en ingeniería de IA, después del prompt engineering y el context engineering, y es el foco principal de inversión de ingeniería en 2026. El principio que lo guía, atribuido a Mitchell Hashimoto, es simple: cada vez que un agente comete un error, se invierte tiempo en diseñar una solución estructural para que el agente nunca vuelva a cometer ese mismo error — casi siempre esa solución es una mejora del harness, no del prompt.

Las cinco capas de un harness de producción

Un harness de nivel producción contiene cinco capas: orquestación de herramientas, bucles de verificación, contexto y memoria, guardrails, y observabilidad. Te las desgloso: 
Faros

Tool orchestration — qué herramientas tiene el agente, cómo decide cuándo usarlas, permisos de invocación (MCP es el estándar emergente para esto).
Verification loops — no basta con que el agente actúe; necesita mecanismos de plan → ejecutar → verificar, con gates de validación antes de comprometerse a la siguiente acción.
Context & memory management — qué ve el agente en cada momento, compactación progresiva cuando el contexto crece, memoria persistente entre sesiones.
Guardrails — límites explícitos de seguridad, aprobación humana en decisiones de alto riesgo, políticas de qué NO puede hacer el agente sin supervisión.
Observability — trazas, logs de auditoría, control de costos, métricas de qué está fallando y por qué.
Inner harness vs. outer harness

Una distinción útil: los labs frontera (como Anthropic) construyen el "Inner Harness" — las capas de seguridad fundamentales, el tool-calling nativo y las ventanas de contexto crudas embebidas en el modelo base. Tú, como equipo de producto, construyes el Outer Harness: todo lo que envuelve a ese modelo para tu caso de uso específico — tus herramientas, tu memoria, tus políticas, tu UX. 
Medium

Information Layer + Feedback Layer

Otro framing útil trata el harness como un sistema de capas entrelazadas: la Information Layer dicta exactamente qué datos puede observar el agente y qué herramientas tiene autorización de invocar en cada momento preciso, usando un mecanismo de "Progressive Disclosure" (no le muestras todo el contexto disponible de una vez, sino lo que necesita en cada paso). La Feedback Layer captura las correcciones humanas cuando el agente falla, las empareja con la trayectoria fallida, y las convierte dinámicamente en una regla activa que se guarda en el banco de memoria para futuras iteraciones — así el sistema aprende de sus errores sin reentrenar el modelo.

Aproximación práctica para tu ecosistema

Te propongo un enfoque en fases, pensado para un ecosistema de desarrollo con IA (varios agentes/herramientas colaborando):

Fase 1 — Define el "loop" central

Antes de cualquier código, decide el patrón de ejecución: la mayoría de harnesses serios usan un bucle Plan → Execute → Verify acotado (bounded loop), no razonamiento libre sin control. La idea es que el harness sea la capa arquitectónica responsable de traducir el razonamiento probabilístico en acción determinística y confiable. 
Medium

Fase 2 — Diseña el registro de herramientas (tool layer)
Usa MCP como capa de acceso a herramientas si vas a integrar múltiples servicios (repos, CI, bases de datos, APIs internas).
Define permisos granulares por herramienta y por agente: qué puede leer, qué puede escribir, qué requiere aprobación humana.
Empieza con herramientas que el modelo ya conoce bien (bash, edición de archivos, git) antes de inventar interfaces custom — esto reduce fricción de aprendizaje del propio modelo.
Fase 3 — Contexto y memoria
Diseña compactación progresiva: a medida que crece el contexto de una tarea larga, necesitas estrategias de resumen/poda (esto es lo que hace, por ejemplo, Claude Code internamente con múltiples etapas de compactación).
Decide qué persiste entre sesiones (memoria a largo plazo) vs. qué es efímero por tarea.
Si tienes subagentes, aísla su contexto — cada uno debería reconstruir su propio contexto de permisos, no heredar todo el del agente padre.
Fase 4 — Guardrails y control humano
Define explícitamente los "gates" de aprobación humana: acciones irreversibles, cambios en producción, gasto de dinero, etc.
Estos guardrails deben ser deterministas (código, no "pídele amablemente al modelo que tenga cuidado").
Fase 5 — Observabilidad y ciclo de mejora
Cada fallo del agente debe quedar trazado y ser diagnosticable: ¿fue el modelo o fue el harness?
Aplica el principio de Hashimoto: cuando encuentres un fallo recurrente, no lo "arregles" solo con un mejor prompt — pregúntate si necesitas una nueva verificación, una nueva herramienta, o un guardrail nuevo.
Métricas útiles: tasa de éxito por tipo de tarea, costo por tarea completada, tasa de intervención humana necesaria.
Fase 6 — Evolución del harness

Un punto importante y contraintuitivo: a medida que las capacidades del modelo mejoran, hay que remover las asunciones y andamiaje ("scaffolding") del harness que ya no son necesarias — un harness diseñado para un modelo débil puede volverse una camisa de fuerza innecesaria para uno más capaz.

El campo es literalmente de este año — el término "harness engineering" entró al uso corriente recién a inicios de 2026, así que no hay todavía un framework único "canónico". El planner es solo uno de tres roles dentro del loop, y conviene tenerlos claros desde ahora aunque implementes el planner primero.

¿Agente o skill? Depende de tu ecosistema:

Skill (prompt + instrucciones estructuradas, sin loop propio) si el planner va a vivir dentro de un agente más grande que ya orquesta el ciclo completo — por ejemplo, si estás construyendo sobre Claude Code o un runtime existente y solo necesitas que, en el paso de planificación, el modelo razone con una plantilla específica y devuelva un formato fijo.
Agente independiente (con su propio prompt de sistema, quizás su propio modelo o temperatura, y una interfaz de entrada/salida bien definida) si en tu ecosistema el planner va a ser invocado por distintos ejecutores, o si quieres poder auditarlo, testearlo y versionarlo por separado del resto del harness.

Mi recomendación por defecto: trátalo como un componente con contrato explícito, no importa si al final lo implementas como skill o como agente separado. Es decir, define:

Input del planner

El objetivo/tarea en lenguaje natural
Contexto relevante (código, historial de conversación, estado del sistema)
El catálogo de herramientas disponibles (qué puede pedir que se ejecute, no cómo ejecutarlo — eso es trabajo del executor)
Restricciones (presupuesto de pasos, políticas de seguridad, qué requiere aprobación humana)

Output del planner

Un plan estructurado, no prosa libre. Normalmente una lista de pasos con: descripción, herramienta sugerida, criterio de éxito de ese paso, y dependencias entre pasos (esto habilita paralelismo y reintentos localizados en vez de repetir todo el plan si falla un paso).
Idealmente en JSON o un esquema fijo — esto es clave porque el executor y el verifier van a consumir esa salida programáticamente, no interpretarla como texto libre.

Una decisión de diseño importante: ¿el planner planifica todo de una vez (plan completo por adelantado) o planifica de forma incremental (un paso o unos pocos, observa el resultado, replanifica)? Para tareas cortas y predecibles, plan completo por adelantado es más barato y más fácil de verificar. Para tareas largas o con mucha incertidumbre (el resultado del paso 2 determina si el paso 3 tiene sentido), conviene replanificación incremental — el planner se vuelve a invocar después de cada verificación, no solo cuando algo falla.

Ya tienes el esqueleto de un harness real: Planner → fases con verificación → agente escéptico como bucle de corrección. Eso es literalmente Plan-Execute-Verify con un critic loop encima. Lo que falta son las piezas que hacen que esto sea robusto en vez de artesanal. Te lo organizo por capas, señalando gaps concretos de tu flujo actual:

1. El plan necesita ser estructurado, no solo un .md narrativo

Si el planner escribe fases en prosa dentro de un markdown, tu skeptic y tu executor tienen que "interpretar" ese texto cada vez. Eso es frágil. Conviene que el planner emita, además del .md legible para ti, un JSON estructurado por fase con:

json
{
  "fase": "2",
  "titulo": "...",
  "pasos": [...],
  "criterio_de_exito": "descripción verificable, no ambigua",
  "herramientas_permitidas": ["postman_mcp", "db_mcp"],
  "estado": "pendiente"
}

Esto te desbloquea dos cosas: (a) puedes automatizar más verificación en vez de que todo dependa del juicio del skeptic, y (b) puedes trackear estado de ejecución programáticamente en vez de mentalmente.

2. El punto más frágil: "si está malo, se corrige hasta que está bien"

Esto es un bucle sin límite y sin memoria entre intentos. Dos riesgos reales:

Bucle infinito o costoso: si el skeptic nunca queda satisfecho, gastas tokens sin fin.
Pérdida de contexto entre correcciones: si el intento 3 no "recuerda" por qué fallaron los intentos 1 y 2, puede repetir el mismo error o corregir un problema introduciendo otro (regresión).

Te muestro cómo se vería con un límite de reintentos y memoria de fallos:

Concretamente:

Límite de reintentos por fase (ej. 3), configurable según el riesgo de la fase.
Historial de fallos acumulado: cada intento fallido guarda qué dijo el escéptico y qué se intentó corregir, para que el intento N+1 no repita el mismo error ni deshaga una corrección anterior.
Escalación a humano en vez de reintento infinito cuando se agotan los reintentos — esto es un guardrail, no una skill, va en código determinista alrededor del agente.
3. Tu paso "verificar manualmente" es el mayor cuello de botella

Dijiste que cada fase tiene un paso de verificar manual. Esto está bien como red de seguridad al principio, pero no escala. La mejora natural:

Para cada fase, define criterios de éxito verificables por herramienta cuando sea posible (ej. "el endpoint devuelve 200 y el campo X existe" → lo verifica el MCP de Postman directamente, no un humano ni el LLM).
Reserva la verificación manual (o el escéptico) para juicios que sí requieren criterio — legibilidad de código, decisiones de diseño, ambigüedad de negocio.
Así conviertes "verificar" en dos sub-capas: verificación determinista (rápida, barata, automática) + verificación por juicio (el escéptico, más cara, reservada para lo que realmente lo necesita).
4. Permisos de tus MCP (Postman + DB)

Esto es un guardrail que probablemente te falta: ¿tu agente puede ejecutar cualquier request de Postman o cualquier query de la DB, o tiene un scope limitado por fase? Si el planner define herramientas_permitidas por fase (como en el JSON de arriba), puedes restringir en tiempo de ejecución qué colección de Postman o qué tipo de query (solo SELECT vs. también UPDATE/DELETE) está autorizada en cada fase — evita que un error de razonamiento del agente termine escribiendo en la DB cuando solo debía consultar.

5. Lo que probablemente no tienes todavía: observabilidad

¿Estás guardando en algún lado el histórico de: plan generado, resultado de cada fase, veredictos del escéptico, cuántos reintentos tomó cada fase? Sin esto no puedes aplicar el principio central de harness engineering — "cuando el agente falla, mejoras el harness para que no vuelva a fallar así" — porque no tienes de dónde sacar el patrón del fallo.

Buena aclaración — eso significa que ya tienes la mitad de la observabilidad, solo que en formato humano y manual. La mejora es simple pero importante: que ese guardado deje de ser algo que tú pides y se vuelva parte automática del contrato del harness — y que además de humano-legible (.md) tengas una capa estructurada (JSON) que el propio sistema pueda leer para tomar decisiones (¿cuántos reintentos van?, ¿qué falló antes?).

Esquema del plan (lo que emite el planner)
json
{

  "fases": [
    {
      "id": "fase_1",

requiere_verificacion_manual es clave: así el planner mismo marca qué fases necesitan tu ojo humano y cuáles pueden cerrarse solo con el escéptico + verificación determinista. Esto te deja elegir, fase por fase, cuánta autonomía le das.

Esquema del estado de fase (fase_state.json) — esto es lo que habilita el límite de reintentos con memoria
json
{
  "fase_id": "fase_1",
  "estado": "en_correccion",
  "intento_actual": 2,
  "max_reintentos": 3,
  "historial_fallos": [
    {
      "intento": 1,
      "razon": "El endpoint no valida el campo email antes de guardar en DB",
      "correccion_aplicada": "Se agregó validación de formato de email con regex"
    }
  ]
}

Este historial_fallos es lo que le pasas al agente corrector en el intento 2 — así el prompt del corrector incluye explícitamente "esto ya se intentó y esto es lo que falló", en vez de partir de cero cada vez.

Una decisión que te toca tomar antes de seguir: ¿quién escribe estos archivos JSON — el propio agente planner/escéptico como parte de su output (le pides que además del .md devuelva el JSON en el mismo turno), o un wrapper de código alrededor del agente que parsea su respuesta y arma los archivos? Yo recomiendo lo segundo: que el agente devuelva solo el JSON estructurado con un campo documentacion_md adentro, y que un script tuyo se encargue de separar eso en los dos archivos (.md + veredicto.json) y de manejar el conteo de reintentos. Así el agente no tiene que "acordarse" de gestionar archivos ni contadores — eso es trabajo determinista, no de LLM.
